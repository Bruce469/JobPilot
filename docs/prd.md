## 1. 背景与目标

### 背景
秋招季（2026 届）投递岗位数量大、节奏快，普遍会遇到：

- 同时投递几十到上百个岗位，公司、岗位、链接、截止日期分散在各处，容易漏投、漏跟进。
- 找岗位时不知道目标公司官网的招聘入口在哪，逐个去官网翻 careers 页效率低、易遗漏。
- 每个岗位的流程状态（简历筛选 → 笔试 → 一面 → 二面 → HR 面 → Offer/拒绝）各不相同，靠记忆或表格维护成本高、易混乱。
- 笔试/面试时间、截止日期临近时缺少提醒，出现过期或爽约风险。
- 每个岗位需要定制简历，版本繁多（通用版/算法版/后端版…），记不清哪个岗位投了哪版、哪版效果更好。
- 想复盘「投了多少、到哪一步挂掉、哪个渠道转化好」，但没有数据支撑。

### 目标
- 一个自用的岗位投递管理网页，投递全程的信息和进度集中一处管理。
- 可量化的目标：
  - 投递记录录入 1 分钟内完成（每条岗位）。
  - 看板上一屏看清全部岗位的状态分布与下一步动作。
  - 截止日期、笔试/面试时间临近时有提醒，零错过。
  - 随时导出一键备份数据，换设备不丢。
  - 简历按岗位定制并导出 PDF，1 分钟内完成。
  - 添加目标公司后 1 分钟内完成官网招聘页探测与岗位抓取导入。

### 产品形态（关键假设 A1）
前后端分离：
- **前端**：单页应用（SPA），负责岗位管理、看板、简历管理、筛选统计等界面与交互。
- **后端**：本机运行的轻量服务，负责公司官网招聘页的探测与岗位抓取（浏览器跨域限制下纯前端无法直接抓取外部网站），并提供数据存储 API。
- **数据存储**：本地 SQLite（数据仅存本机），前端通过后端 API 读写。
- **部署形态**：后端默认本机运行（127.0.0.1），浏览器打开前端即用；无需注册登录（个人工具）。
**若后续需要多设备同步或手机访问，把后端部署到个人服务器即可，见 7. 开放问题 Q1。**

## 2. 目标用户与场景

### 用户画像
- 本人，正在经历 2026 秋招季的应届生，投递量预估 30–100 个岗位。
- 会使用浏览器和 Excel，但希望比表格更直观、更少手工维护。

### 核心场景
1. **发现/录入**：添加目标公司后一键抓取其官网招聘页岗位；或看到心仪 JD 后 1 分钟内手动录入公司、岗位、链接、截止日期。
2. **跟踪**：每天打开看板，查看「今天/本周有哪些笔试面试」「哪些已投递待跟进」。
3. **推进**：收到笔试/面试/结果后，一键流转状态并记录时间与备注。
4. **复盘**：月末看统计面板，了解投递量、各环节转化、各渠道效果。
5. **备份/迁移**：导出数据文件，或换电脑导入继续用。

## 4. 功能需求

> 每个功能给出用户故事与 Given-When-Then 验收标准。字段名以 4.1 字段表为准。

### 4.0 岗位数据模型（字段表）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | string | — | 唯一 ID，后端生成（UUID） |
| company | string | 是 | 公司名称（名称快照，创建时唯一必填项） |
| company_id | string | 否 | 关联公司库（4.12）的可空外键；从公司库导入/选择公司时自动写入 |
| position | string | 否 | 岗位名称 |
| job_type | enum | 否 | 岗位类型：校招 / 社招 / 实习（抓取时尽力解析） |
| degree | string | 否 | 学历要求：本科 / 硕士 / 博士（抓取时尽力解析） |
| city | string | 否 | 意向城市（支持多值 / 全国） |
| industry | string | 否 | 行业类别（互联网/金融/国企/外企/制造业/其他，支持自定义），抓取导入时自动带入 |
| channel | enum | 否 | 投递渠道：官网 / Boss直聘 / 牛客 / 内推 / 邮箱 / 其他（抓取导入默认「官网」） |
| job_url | string | 否 | JD 直链（抓取导入时自动带入岗位链接） |
| source_job_id | string | 否 | 外部招聘系统职位 ID（抓取去重主键，可空） |
| publish_date | date | 否 | 职位发布日期（区别于录入时间） |
| deadline | date | 否 | 投递截止日期 |
| applied_at | date | 否 | 实际投递时间（状态转入「已投递」时自动记录，统计趋势依据） |
| status | enum | 是 | 状态（见 4.2，创建默认「待投递」） |
| ended_at | date | 否 | 结束日期（进入终态时自动记录，回退时清除） |
| resume_id | string | 否 | 所投简历 ID（关联 4.11 简历） |

| notes | array | 否 | 备注/面经多段记录 `[{time, content}]`（M1 定结构，M2 出界面） |
| events | array | 是 | 时间线（可为空数组）：`[{time, type, from_status?, to_status?, note}]`，type ∈ {状态流转, 笔试, 面试, 备注}（M1 即记录） |

### 4.1 岗位记录管理（Must）

**用户故事**：作为求职者，我想要快速录入和修改岗位信息，以便投递过程有据可查。

- 描述：新增、编辑、删除岗位记录；删除需二次确认；支持批量删除（多选）。
- 业务规则：
  - 公司名必填，其余字段可选。
  - 状态默认「待投递」。
  - 删除为**硬删除 + 二次确认**；应用启动时若距上次成功导出 > 7 天，站内提示备份（防误删的最后防线，机制见 4.7）。
- 验收标准：
  - Given 看板页，When 点击「新增岗位」并填写公司名，Then 生成一条默认状态为「待投递」的记录并进入列表。
  - Given 一条岗位记录，When 点击编辑并修改字段后保存，Then 该记录字段更新且 updated_at 刷新。
  - Given 一条岗位记录，When 点击删除，Then 弹出确认框，确认后该记录被移除。
  - Given 列表页勾选多条记录，When 点击批量删除并确认，Then 所选记录全部移除。

### 4.2 流程状态管理（Must）

**用户故事**：作为求职者，我想要跟踪每个岗位到哪一步了，以便知道下一步该做什么。

- 描述：状态机流转 + 时间线记录，每次流转自动写一条事件。
- 状态定义：
  状态全集：`待投递 / 已投递 / 简历筛选 / 笔试 / 一面 / 二面 / 三面/HR面 / 已Offer / 已拒绝 / 已放弃`。
  **终态 = {已Offer, 已拒绝, 已放弃}**，可从任意非终态到达（如一面后直接放弃），不做强制顺序校验（现实流程多变）。
- 业务规则：
  - 状态可前进、可回退（如「一面」改判「简历筛选」）；每次状态变更自动写入 events 时间线（时间、新旧状态、可选说明）；**同状态重复流转不产生新事件**。
  - 进入终态时自动记录 ended_at；从终态回退时清除 ended_at。
  - 看板默认不展示已结束岗位，提供「含已结束」开关与终态筛选入口查看。
- 验收标准：
  - Given 一条「已投递」状态的记录，When 将状态改为「笔试」并保存，Then 状态更新且时间线新增一条「已投递 → 笔试」事件。
  - Given 任意记录，When 回退状态，Then 允许操作且时间线如实记录，不报错。
  - Given 一条记录状态变为「已拒绝」，Then 该记录默认移出看板主视图，统计中计入「已拒绝」。

### 4.3 关键日期管理与展示（Must）

**用户故事**：作为求职者，我想要一眼看到截止日期和笔试面试安排，以便不错过任何节点。

- 描述：deadline（投递截止）为独立字段；笔试/面试时间作为 events 中的事件（type=笔试/面试，携带时间）录入与管理；看板顶部显示「今日/本周安排」（从 events 聚合）与「即将截止」。
- 业务规则：
  - 「即将截止」= 距 deadline ≤ 3 天且未到终态。
  - 已过期的笔试/面试事件（事件时间早于当前且状态未流转）在列表中标红提醒。
- 验收标准：
  - Given 一条记录设置了截止日期为今天，When 打开看板，Then 顶部「即将截止」区显示该公司与岗位。
  - Given 一条记录的笔试时间已过且状态未流转，When 打开列表，Then 该记录显示过期提醒标识。

### 4.4 看板与列表视图（Must）

**用户故事**：作为求职者，我想要按状态一屏看清所有岗位，以便快速定位当前重心。

- 描述：两种视图可切换。
  - 看板：按状态分列（看板列），卡片可拖拽改变状态（拖拽即流转，等价 4.2）。
  - 列表：表格形式，列可排序（按公司、更新时间、截止日期、投递时间）。
- 业务规则：拖拽流转与手动改状态效果一致，均写时间线；拖拽到同一列不产生事件。
- 验收标准：
  - Given 看板页，When 将某卡片从「已投递」列拖到「笔试」列，Then 状态更新且时间线记录事件。
  - Given 列表页，When 点击「截止日期」列头，Then 记录按截止日期升/降序排列。

### 4.5 搜索与筛选（Must）

**用户故事**：作为求职者，我想要按公司/状态/城市/关键词找岗位，以便快速定位。

- 描述：搜索框（匹配公司、岗位名）+ 筛选（状态、城市、渠道、行业）。筛选条件多选可组合，支持一键清除。
- 验收标准：
  - Given 列表页有 50 条记录，When 输入公司关键词，Then 仅显示公司名匹配的记录。
  - Given 已勾选「状态=笔试」筛选，When 查看列表，Then 仅显示笔试状态记录，且筛选条件可见可一键清除。
  - Given 已勾选「城市=北京」+「行业=互联网」筛选，When 查看列表，Then 仅显示同时满足两项的记录。
  - Given 已勾选「渠道=官网」+「城市=北京」筛选，When 查看列表，Then 仅显示同时满足两项的记录。

### 4.6 本地存储与持久化（Must）

**用户故事**：作为求职者，我想要数据存本机且刷新、重启不丢，以便安心使用。

- 描述：所有业务数据经本机后端 API 落盘 SQLite（本机文件）；每次变更自动保存；刷新页面/重启后端后数据完整保留。localStorage 仅用于非业务瞬时状态（筛选条件、视图偏好等）。
- 业务规则：数据仅存本机（本机运行模式下），不对外传输；手动备份归 4.7 导出。
- 验收标准：
  - Given 已录入多条记录，When 刷新页面并重启后端后重新打开，Then 数据完整保留。
  - Given 任意数据状态，When 点击「导出 JSON」，Then 下载包含全部记录（岗位/公司/简历）的备份文件。

### 4.7 数据导入 / 导出（Must）

**用户故事**：作为求职者，我想要导出备份并在新设备恢复，以便换电脑不丢数据。

- 描述：导出 JSON（全量：岗位、公司、简历三个集合，文件含 schema_version）；导入 JSON（覆盖或合并两种模式，默认合并，按 id 去重）。导出/导入由后端 API 提供。
- 业务规则：
  - 导入前校验文件格式、schema_version 与必填字段，非法文件给出明确错误提示，不破坏现有数据。
  - **合并模式：同 id 冲突以本机现有数据为准，备份中同 id 记录跳过并计入跳过数**；覆盖模式为全量替换，需二次确认。
  - 备份范围含全部三个集合，导入后岗位对简历/公司的引用按 id 恢复，无引用对象时置空。
- 验收标准：
  - Given 一份合法备份文件，When 导入（合并模式），Then 现有记录保留、备份中的新记录被添加，重复 id 不产生两条。
  - Given 一份非 JSON 或字段缺失的文件，When 导入，Then 提示「文件格式不正确」，现有数据不受影响。
  - Given 合并模式下备份中存在与本地同 id 但内容不同的记录，When 导入，Then 以本机数据为准，该记录计入跳过数。

### 4.8 统计面板（Should，M2）

**用户故事**：作为求职者，我想要看到投递漏斗和渠道效果，以便复盘秋招策略。

- 描述：卡片式统计：总投递数、进行中、已 Offer、已拒绝、待跟进数；漏斗图（各状态人数）；渠道分布饼图；近 4 周投递趋势柱状图。
- 业务规则（指标口径）：
  - 总投递数 = 已投递及之后状态的记录；进行中 = 已投递至三面/HR面且未到终态；待跟进数 = 已投递且距上次流转 > 3 天；已Offer / 已拒绝按终态计（含已放弃）。
  - 近 4 周投递趋势按 applied_at 统计；漏斗层级从「已投递」起、不含「待投递」。
- 验收标准：
  - Given 有 20 条记录（含各状态），When 打开统计页，Then 各卡片数字与记录一致，漏斗按状态逐级展示。
  - Given 无任何数据，When 打开统计页，Then 显示空态引导文案而非报错。

### 4.9 提醒（Should，M2）

**用户故事**：作为求职者，我想要在截止/笔试/面试前收到提醒，以便不错过安排。

- 描述：站内倒计时 + 浏览器通知（Notification API，需用户授权）；提醒规则：截止前 24h、笔试/面试前 2h 与 24h（与 4.3 看板「即将截止 ≤ 3 天」展示口径不同，属正常，二者独立）。
- 业务规则：提醒基于当前时刻计算；**同一提醒点（记录+时间点）只触发一次，触发后标记，不因页面刷新重复弹出**；页面关闭期间错过的提醒，下次打开补一条站内提示；页面关闭时仅靠浏览器通知（可能失效，标注局限，见 7. Q2）。
- 验收标准：
  - Given 页面打开且通知已授权，When 有距笔试 2 小时的记录，Then 触发一次浏览器通知。
  - Given 通知未授权，When 打开设置，Then 引导用户授权并说明仅本机可见。

### 4.10 备注 / 面经记录（Should，M2）

**用户故事**：作为求职者，我想要记录每轮笔试面试的复盘，以便后续面试针对性准备。

- 描述：每条记录可追加多段备注（存于 notes 数组 `[{time, content}]`，与 4.0 一致），按时间排序；支持 Markdown 简单格式（标题、列表）。
- 验收标准：
  - Given 一条记录，When 添加一段面经并保存，Then 该段按时间追加显示且可编辑删除。

### 4.11 简历管理与生成（Must，M1）

**用户故事**：作为求职者，我想要维护多份简历并按岗位导出 PDF，以便对不同岗位投递最合适的简历。

- 描述：
  - 简历列表：多份简历 CRUD。每份简历包含结构化区块：基本信息（姓名、电话、邮箱、意向岗位、城市）、教育经历、实习经历、项目经历、技能标签、自我评价。
  - 简历生成：从简历数据渲染为 A4 简历页面，支持浏览器打印 / 另存为 PDF（MVP 用 `window.print()` + 打印样式，零外部依赖）。
  - 版本绑定：岗位记录可关联一份简历，记录"该岗位投的是哪版"（原 Should 项升级）。
- 简历数据模型（独立于岗位数据）：

  | 字段 | 类型 | 必填 | 说明 |
  |---|---|---|---|
  | id | string | — | 唯一 ID，自动生成 |
  | name | string | 是 | 简历名称（如「简历 v2-算法岗」） |
  | basic | object | 是 | 姓名 / 电话 / 邮箱 / 意向岗位 / 城市 |
  | education | array | 否 | 教育经历：学校 / 专业 / 学历 / 起止时间 / 说明 |
  | experience | array | 否 | 实习经历：公司 / 岗位 / 起止时间 / 职责与成果 |
  | projects | array | 否 | 项目经历：名称 / 角色 / 起止时间 / 描述 |
  | skills | array | 否 | 技能标签列表 |
  | summary | string | 否 | 自我评价 |
  | created_at | datetime | 是 | 创建时间 |
  | updated_at | datetime | 是 | 最后编辑时间 |

- 业务规则：
  - 简历与岗位记录相互独立：编辑简历不影响任何岗位记录；岗位仅存简历 id + 名称快照。
  - 简历名称必填；至少有一个区块有内容才可导出。
  - 删除简历需二次确认；若已被岗位引用，提示"N 个岗位绑定此简历"，确认后这些岗位的绑定置空。
  - PDF 导出走浏览器打印功能（打印样式按 A4 排版），不依赖第三方服务。
- 验收标准：
  - Given 简历管理页，When 新建简历并填写基本信息、一段教育经历后保存，Then 简历出现在列表中且内容可再次编辑。
  - Given 一份内容完整的简历，When 点击「导出 / 打印」，Then 打开打印预览、按 A4 简历版式排版，可另存为 PDF。
  - Given 岗位编辑页存在多份简历，When 选择「简历 v2-算法岗」并保存，Then 该岗位显示绑定版本名称。
  - Given 一份被 3 个岗位引用的简历，When 点击删除并确认，Then 提示引用数量、简历被删除、3 个岗位的绑定变为「未绑定」。

### 4.12 公司库与官网抓取（Must，M1）

**用户故事**：作为求职者，我想要把目标公司加入公司库并一键获取其官网招聘页岗位，以便快速发现可投递机会、不遗漏心仪公司。

- 描述：
  - 公司库 CRUD：维护目标公司清单（名称、官网地址、行业、备注）。
  - 手动录入 + **批量导入**：可手动逐个添加；也可选择 txt 文件（每行一个公司名）批量导入，去空行、去重、跳过已存在公司。
  - **按名称自动补全**：仅输入公司名称时，系统自动获取官网地址（website）、行业（industry）、招聘页链接（career_url）——优先命中内置常见公司映射表（覆盖主流大厂/国企/外企），未命中时通过搜索引擎解析官网域名，再复用招聘页探测能力获取 career_url；行业匹配不到时留空由用户手填。单个公司同步补全；批量补全走异步任务（复用任务轮询）。
  - 官网招聘页自动探测：给定官网地址自动解析招聘入口。探测顺序：首页链接扫描（a[href] 含 careers/jobs/招聘/加入我们）→ robots.txt 的 Sitemap 条目 → sitemap 中含 career/job/recruit 的 URL → 常见招聘子域候选（talent.*、*.jobs.feishu.cn、campus.* 等）。探测返回候选 URL 列表 + 置信度供人工择一；失败可手动填写，修正值保存后复用。
  - 岗位抓取与导入：从招聘页抓取公开岗位字段（岗位名、城市、行业、岗位直链 job_url、可选 deadline 与外部职位 ID source_job_id），预览确认后批量导入岗位库。
- 公司数据模型：

  | 字段 | 类型 | 必填 | 说明 |
  |---|---|---|---|
  | id | string | — | 唯一 ID |
  | name | string | 是 | 公司名称（唯一，同名拦截） |
  | website | string | 是 | 官网地址（用于探测招聘入口） |
  | career_url | string | 否 | 探测到的招聘页 URL（可人工修正） |
  | industry | string | 否 | 行业类别（导入岗位时自动带入） |
  | probe_status | enum | 否 | 探测状态：未探测 / 成功 / 失败 / 需人工 |
  | ats_type | string | 否 | 识别到的招聘系统类型（如 飞书 / 北森 / Greenhouse / Lever / 通用） |
  | notes | string | 否 | 备注 |
  | last_fetched_at | datetime | 否 | 最近抓取时间 |
  | last_fetch_result | string | 否 | 最近一次抓取结果摘要（如「新增 5 条，跳过 2 条」） |
  | created_at | datetime | 是 | 添加时间 |

- 业务规则：
  - 抓取仅限公司官网招聘页，不抓取招聘平台；仅解析公开页面，不绕过登录、验证码、付费墙；抓取前先请求该域名 robots.txt，Disallow 则跳过并提示。
  - 限速量化：串行抓取（并发=1）、同域名请求间隔 ≥ 1.5s、全局 ≤ 30 请求/分钟、固定 User-Agent 标识个人工具。
  - **「探测 + 抓取」为后端异步任务**：立即返回 job_id，前端轮询进度；单 HTTP 请求超时 < 10s，单公司整任务上限 60s，超时降级为「保留招聘页链接 + 手动录入」。
  - 去重规则（导入时）：优先按 source_job_id 命中（重复抓取必命中）；无 source_job_id 时按 company_id（或归一化公司名）+ 规范化岗位名 + city 判定。岗位名规范化：去除【】内批次前缀、「急聘/热招」等后缀、空格与全半角差异。公司名归一化：去除「有限公司/股份/（中国）」等后缀。
  - 解析失败/部分成功均有明确反馈：导入结果提示「新增 N 条、跳过 M 条、失败 K 条（附原因）」；解析到 0 条岗位给出原因提示。
  - **官网已删除的岗位保留本机记录**（导入不改动现有岗位）；重复点击「抓取」幂等，不重复写入。
  - 批量导入规则：txt 每行一个公司名；空行与首尾空格忽略；与已有公司重名（归一化后）跳过并计数；结果提示「新增 N 条、跳过 M 条」。
  - 自动补全规则：补全结果**需用户确认后可保存**（防错配）；补全失败（映射表未命中且搜索失败）明确提示，公司记录仍可保存、后续手动修正；搜索兜底复用抓取限速。
- 验收标准：
  - Given 公司库为空，When 添加公司「字节跳动」及官网地址，Then 系统探测并保存其招聘页链接（探测失败时提示并允许手动填写）。
  - Given 一个含 3 个公司名（含空行与重复项）的 txt 文件，When 导入，Then 新增去空行去重后的公司，重复名计入跳过数。
  - Given 输入公司名「字节跳动」，When 触发自动补全，Then 返回官网/招聘页/行业并回填表单（映射表命中，可编辑后保存）。
  - Given 输入一个不在映射表内的公司名且搜索失败，When 触发自动补全，Then 提示获取失败、允许手动填写保存。
  - Given 某公司招聘页可解析，When 点击「抓取岗位」，Then 展示岗位预览列表（岗位名/城市/直链），确认后导入岗位库并标注去重结果。
  - Given 同公司同岗位名已存在，When 再次抓取导入，Then 该岗位被跳过并计入跳过数，不产生重复记录。
  - Given 官网为 JS 动态渲染或强反爬页面，When 抓取，Then 提示解析失败原因并降级为手动录入，不影响其他功能。
  - Given 某公司官网已删除某岗位，When 重复抓取，Then 本机该岗位记录保留不变，仅计数新增/跳过。

## 7. 风险与开放问题

### 风险
| 风险 | 影响 | 缓解 |
|---|---|---|
| 时间/范围风险：M1 过重且个人时间被秋招挤占 | 高 | P0 > P1 > P2 裁减策略；M1 预留 2 天 buffer；「可用 MVP」验收标准明确 |
| 公司官网页面结构多变、解析失败 | 中 | 解析失败降级为「保留招聘页链接 + 手动录入」；解析器按常见模式设计并随使用持续适配 |
| 抓取触发官网反爬 / 频率限制 | 中 | 低频限速、遵守 robots.txt、仅个人使用；必要时人工浏览后手动录入 |
| SQLite 数据文件损坏/丢失 | 中 | 启用 WAL 模式；后端导出 JSON 为主备份；启动时检查距上次导出 > 7 天提示 |
| 提醒在页面关闭后失效 | 中 | 站内倒计时为主，浏览器通知为辅；错过提醒下次打开补发（见 4.9） |
| 官网招聘页 URL 探测不准确 | 低 | 探测结果可人工修正，修正值保存后后续复用 |
| 自动补全可靠性：映射表覆盖面有限、搜索兜底可能失败或限流 | 中 | 预置常见公司映射表（主流大厂/国企/外企）；搜索失败明确提示、留空手填；结果需确认后保存 |
| 简历打印分页跨浏览器差异 | 低 | 默认 window.print() 方案，PDF 版式为人工验收项（见 Q6） |
| 本地后端端口占用/多实例冲突 | 低 | 随机可用端口 + 启动失败明确提示 |

### 开放问题
- **Q1（影响架构）**：后端部署形态 —— 本机运行（127.0.0.1，数据不出本机）vs 部署到个人服务器（可手机访问、支持定时抓取）？**默认本机运行**，需要同步时再部署（部署公网需补鉴权，MVP 不做）。
- **Q2（影响体验）**：提醒的接受度 —— 只做站内 + 浏览器通知，还是本机后端加定时任务（应用开着即可准时提醒）？默认前者，后端定时任务作为 M3 可选增强。
- **Q3（影响实现）**：技术选型 —— **已定稿：前端 Vite + Vue 3 + TypeScript（Pinia + Vue Router）；后端 Python + FastAPI + SQLite（抓取解析用 httpx + BeautifulSoup，数据校验用 Pydantic）**。前后端通过 REST API 对接，接口契约不受语言影响。
- **Q4（影响优先级）**：Excel 导入 —— **已定稿：无存量投递表，维持 M3（Could 级）**。
- **Q5**：是否需要「意向度 / 优先级」字段（如 高/中/低），用于加急排序？默认用 4.13 收藏置顶替代，后续需要时增量加 priority 字段。
- **Q6（影响实现）**：简历 PDF 导出方案 —— 默认浏览器打印（window.print，零依赖）；若分页不可控再评估 html2pdf.js / jsPDF。PDF 版式为人工验收项。
- **Q7（影响体验）**：简历模板数量 —— MVP 先做 1 套默认 A4 模板，还是直接做 2–3 套可切换？默认 1 套，M2/M3 视使用感受补充。
- **Q8（影响抓取）**：官网抓取解析策略 —— 已定分层方案：probe（robots/sitemap/首页/子域）→ ATS 识别 → 适配器（**M1 做 Greenhouse/Lever/飞书招聘 + JSON-LD 兜底**，北森/Moka/大易归 M2）→ 人工录入兜底。**不引入无头浏览器**（依赖重且对强反爬站点无效）。
